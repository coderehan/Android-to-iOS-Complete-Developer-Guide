# 05 - UI: Jetpack Compose vs SwiftUI

> If you've made the jump from XML to Compose, you already made the hard conceptual leap — SwiftUI feels like a close cousin of Compose, not a different species.

---

## 🔑 Core Philosophy

| Jetpack Compose | SwiftUI |
|---|---|
| Declarative UI in Kotlin | Declarative UI in Swift |
| `@Composable` functions | `View` protocol / `struct: View` |
| Recomposition on state change | Re-render on `@State`/`@Published` change |
| `Modifier` chain | View modifier chain |
| Compose Preview | Canvas / `#Preview` |

Both frameworks replaced an older imperative UI toolkit (Android View system → Compose, UIKit → SwiftUI) with a declarative, function/struct-based model where the UI is a function of state.

---

## 🧩 Basic Component

**Jetpack Compose**
```kotlin
@Composable
fun Greeting(name: String) {
    Text(
        text = "Hello, $name!",
        fontSize = 20.sp,
        color = Color.Blue
    )
}
```

**SwiftUI**
```swift
struct Greeting: View {
    let name: String

    var body: some View {
        Text("Hello, \(name)!")
            .font(.system(size: 20))
            .foregroundColor(.blue)
    }
}
```

A `@Composable` function ≈ a `struct` conforming to `View` with a computed `body`. Both take parameters, both render declaratively, both compose smaller pieces into bigger screens.

---

## 🎨 Modifiers

**Compose**
```kotlin
Text(
    text = "Hello",
    modifier = Modifier
        .padding(16.dp)
        .background(Color.Gray)
        .fillMaxWidth()
)
```

**SwiftUI**
```swift
Text("Hello")
    .padding(16)
    .background(Color.gray)
    .frame(maxWidth: .infinity)
```

Compose applies modifiers via a single `Modifier` parameter chain. SwiftUI chains modifiers directly on the view itself — functionally equivalent, syntactically more fluent (each modifier returns a new wrapped view).

> ⚠️ Order matters in **both** frameworks — `.padding().background()` produces a different result than `.background().padding()`, in both Compose and SwiftUI.

## 📐 Layout Building Blocks

| Compose | SwiftUI |
|---|---|
| `Column { }` | `VStack { }` |
| `Row { }` | `HStack { }` |
| `Box { }` | `ZStack { }` |
| `LazyColumn { }` | `List { }` / `ScrollView { LazyVStack { } }` |
| `LazyRow { }` | `ScrollView(.horizontal) { LazyHStack { } }` |
| `Spacer()` | `Spacer()` |
| `Card { }` | Custom view + `.background()` + `.cornerRadius()` |

## 🖼 Example: A Simple List Screen

**Compose**
```kotlin
@Composable
fun UserListScreen(users: List<User>) {
    LazyColumn {
        items(users) { user ->
            Row(modifier = Modifier.padding(8.dp)) {
                Text(user.name)
            }
        }
    }
}
```

**SwiftUI**
```swift
struct UserListScreen: View {
    let users: [User]

    var body: some View {
        List(users) { user in
            Text(user.name)
                .padding(8)
        }
    }
}
```

`LazyColumn` and SwiftUI's `List` both handle recycling/lazy-loading automatically — you don't manage a `ViewHolder`/cell-reuse pattern manually, unlike old-school `RecyclerView`/`UITableView`.

## 🔘 Buttons & Interaction

**Compose**
```kotlin
Button(onClick = { viewModel.onLoginClicked() }) {
    Text("Login")
}
```

**SwiftUI**
```swift
Button("Login") {
    viewModel.onLoginClicked()
}
```

---

## 🖌 Conditional UI

**Compose**
```kotlin
if (isLoading) {
    CircularProgressIndicator()
} else {
    UserList(users)
}
```

**SwiftUI**
```swift
if isLoading {
    ProgressView()
} else {
    UserList(users: users)
}
```

Identical pattern — plain Kotlin/Swift `if` statements work directly inside the declarative UI tree in both frameworks.
