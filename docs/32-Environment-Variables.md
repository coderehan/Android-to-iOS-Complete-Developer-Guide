# 32 - Environment Variables: BuildConfig vs .xcconfig

> Android auto-generates a `BuildConfig` class from Gradle fields. iOS has no auto-generated equivalent — the standard path is `.xcconfig` files feeding into `Info.plist`, read at runtime via `Bundle.main`.

---

## 🔑 Core Comparison

| Android | iOS |
|---|---|
| `buildConfigField()` in Gradle | Key-value pairs in `.xcconfig` files |
| Auto-generates `BuildConfig.FIELD_NAME` | Injected into `Info.plist` as `$(VARIABLE_NAME)` placeholders |
| Accessed as `BuildConfig.BASE_URL` | Accessed via `Bundle.main.infoDictionary?["BASE_URL"]` |
| Per flavor × build type | Per `.xcconfig` file (usually per environment) |

---

## ⚙️ Defining Environment-Specific Values

**Android**
```kotlin
android {
    productFlavors {
        create("dev") {
            buildConfigField("String", "BASE_URL", "\"https://api.dev.example.com\"")
        }
        create("prod") {
            buildConfigField("String", "BASE_URL", "\"https://api.example.com\"")
        }
    }
}

// Usage
val url = BuildConfig.BASE_URL
```

**iOS**
```
# Config-Dev.xcconfig
BASE_URL = https:/$()/api.dev.example.com   // note: // requires escaping in xcconfig

# Config-Prod.xcconfig
BASE_URL = https:/$()/api.example.com
```

```xml
<!-- Info.plist -->
<key>BaseURL</key>
<string>$(BASE_URL)</string>
```

```swift
// Usage
let url = Bundle.main.infoDictionary?["BaseURL"] as? String ?? ""
```

> ⚠️ Gotcha: `.xcconfig` syntax treats `//` as the start of a comment, so URLs need the escape `$()` trick shown above (`https:/$()/...`) to avoid the comment parser eating the rest of the line.

## 🗂 Assigning Configs per Build Configuration

In Xcode: **Project → Info tab → Configurations** — assign `Config-Dev.xcconfig` to your Debug configuration and `Config-Prod.xcconfig` to Release (or create custom configurations like "Staging" entirely).

Each Scheme can then be tied to a specific Configuration, mimicking Android's flavor × build type matrix, just via a slightly different mechanism (Scheme → Configuration pairing rather than Gradle's automatic cross-product).

## 🔐 Secrets & API Keys

**Android** — often kept out of version control via `local.properties` (gitignored) and read into `buildConfigField` at build time, or via a `secrets.properties` + Secrets Gradle Plugin.

**iOS** — common patterns:
1. A gitignored `Secrets.xcconfig` imported by the main `.xcconfig` files
2. A `.gitignore`'d `Secrets.swift` (generated by a script) with `static let` constants
3. CI injects secrets as environment variables during the build, written into the Info.plist at build time via a Run Script phase

```
// Main.xcconfig
#include "Secrets.xcconfig"
```

Same underlying goal as Android's `local.properties` approach: keep real secrets out of git while making them available at build time.

---

## 🧪 Debug-Only Flags

**Android**
```kotlin
if (BuildConfig.DEBUG) {
    // debug-only logging, etc.
}
```

**iOS**
```swift
#if DEBUG
    // debug-only logging, etc.
#endif
```

Swift's `#if DEBUG` is a **compile-time** conditional (code is stripped entirely from Release builds) — closer to Kotlin's `BuildConfig.DEBUG` combined with R8/ProGuard dead-code elimination than to a simple runtime `if`.

## 📝 Quick Reference Table

| Concept | Android | iOS |
|---|---|---|
| Config definition | `buildConfigField()` | `.xcconfig` key-value |
| Auto-generated accessor | `BuildConfig.FIELD` | None — manual `Bundle.main` lookup |
| Debug-only code | `if (BuildConfig.DEBUG)` | `#if DEBUG` (compile-time) |
| Secrets management | `local.properties` (gitignored) | `Secrets.xcconfig` (gitignored) |
| Per-environment values | Product Flavors | Multiple `.xcconfig` files |
| CI secret injection | Env vars → Gradle properties | Env vars → Run Script → Info.plist |
